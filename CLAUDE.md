# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

openwehr (repo `roberteinsle/openwehr`, name always written in lowercase): a web app for volunteer fire brigades: a core plus modules that each Wehr switches on (Laravel 12, Livewire 4, Filament 5 admin, Tailwind 4 + Alpine + FullCalendar 6 via Vite, Pest 3). Licensed under AGPL-3.0. The UI, emails, validation messages and README are German; code, comments and commit messages are English. The README documents every user-facing behaviour in detail. Read it before changing booking or decision logic, and update it when behaviour changes.

## Commands

```bash
composer setup                 # install, key:generate, migrate, npm build
composer dev                   # artisan serve + queue + pail + vite
composer test                  # config:clear + artisan test
./vendor/bin/pest                                   # all tests
./vendor/bin/pest tests/Feature/Booking/DecisionTest.php
./vendor/bin/pest --filter="admins are asked when there is no decider"    # single test by name
./vendor/bin/pint              # code style (Laravel Pint; not enforced in CI, run it before committing)
./vendor/bin/phpstan analyse --memory-limit=2G   # Larastan level 5, enforced in CI; old findings in phpstan-baseline.neon (never add new code to it)
composer audit && npm audit --omit=dev           # known vulnerabilities, enforced in CI
npm run build                  # production assets
docker compose up --build      # full stack on :8080, mails go to storage/logs/laravel.log
python3 scripts/build-wiki.py <dir> <version>   # GitHub wiki pages from README.md; copy into a clone of openwehr.wiki.git and push
```

**PostgreSQL is mandatory, including for tests.** SQLite and MySQL won't work. `phpunit.xml` expects `pgsql` at `127.0.0.1:5432` with db `openwehr_test`, user `openwehr`, password `secret`. Feature tests use `RefreshDatabase` (see `tests/Pest.php`). CI runs `pest --parallel` against Postgres 18.

The dev container (`.devcontainer/`, used by Codespaces) provides all of this: PHP 8.4 with `pdo_pgsql`/`intl`/`gd`/`exif` in service `app`, PostgreSQL 18 in service `db` sharing its network (so `127.0.0.1:5432` works), and `post-create.sh` creates `.env`, migrates with seed data and the `openwehr_test` database. Inside it, just run `composer test` / `./vendor/bin/pest --parallel`. Log in as `admin@example.com`; the magic link is in `storage/logs/laravel.log`.

Outside the dev container (an old Codespace without it), run tests in throwaway containers:

```bash
docker run -d --name openwehr-test-pg -e POSTGRES_DB=openwehr_test -e POSTGRES_USER=openwehr -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:18
docker run --rm --network host -v "$PWD":/app -w /app --user root -e SHOW_WELCOME_MESSAGE=false serversideup/php:8.4-cli \
  sh -c "install-php-extensions gd intl >/dev/null 2>&1; ./vendor/bin/pest --parallel; chown -R 1000:1000 storage bootstrap/cache"
```

The trailing `chown` matters: root-owned files left in `storage/` break `docker build` (permission denied in the build context).

Test data, seeders and commits use invented people only ("Hanna Hydrant", "Bernd Blaulicht", `example.com` addresses), never names or addresses of real members. The repository is public: no names, addresses, domains, servers or settings of a real Wehr or of the maintainer in code, docs, tests or commit messages (example Wehr: "FF Musterstadt", `ff-musterstadt.de`). The only exceptions are the legally required `docs/impressum.html` and `docs/datenschutz.html` and the `author` in the JSON-LD of `docs/index.html` on the project page (GitHub Pages from `main` /docs, www.openwehr.de), by the maintainer's decision.

## Architecture

### Core and modules
`app/` is the core: users and member data, auth, the start page, notifications, feedback, the activity log and the main Filament panel (`/admin`). Each feature area is a module under `modules/<Name>/` (namespace `Modules\<Name>\`, code in `src/`, so classes are `Modules\<Name>\src\...`). A module has its own `<Name>ServiceProvider` (at the module root, next to `src/`, listed in `bootstrap/providers.php`), plus `routes/web.php`, `database/migrations` (loaded via `loadMigrationsFrom`) and `resources/views` (view namespace = lowercase module key, e.g. `fahrzeugbuchung::`). There is one Filament panel (`/admin`, `AdminPanelProvider`). Modules with admin pages add them through `<Name>Plugin` as a navigation group. Its entry page implements `App\Filament\ModuleArea` (`allows(User)` decides who manages the module): a `<Name>Dashboard` with widgets (extends `ModuleDashboard`, route `/admin/<key>`; Fahrzeugbuchung, Kleiderkammer, Ausrüstung, Mängelmanagement) or a single page (`use IsModuleArea`; the Einstellungen of Einsatzbericht and Personalverwaltung). Further resources and pages get the slug prefix `<key>/` and `use <Name>Area` (access and group from the dashboard). Module settings and management pages belong there, reached by the Modulleiste's `manage` gear, not as tabs. Views of panel pages use Filament components and local CSS (no app Tailwind classes in the panel). Panel-wide additions go through render hooks in `AdminPanelProvider` (user menu e-mail, the Kleiderkammer Scan button `kleiderkammer::partials.scan-button`, which the app layout includes too). Core resources `use App\Filament\Concerns\AdminOnly` and core widgets check `is_admin`, because `User::canAccessPanel` also lets in module managers (`ModuleAreas::for`); `/admin` sends them to their first area. New admin pages must have one of these checks. Module tests are not inside the module: they live in `tests/Feature/<Name>` (Fahrzeugbuchung: `tests/Feature/Booking`).

Modules never reference each other's internals where a core registry exists; they register with these (`app/Services`, singletons, called in `boot()`, each described below): `ModuleRegistry`, `DashboardRegistry`, `ScanRegistry`, `PersonnelFileRegistry`, `VehicleBlockRegistry`, `VehicleBookingRegistry`, `DriverRegistry`, `BadgeRegistry`, `HoursRegistry`, `CredentialRegistry`, `InventoryRegistry`, `AnnualReportRegistry`. For new cross-module features, add to a registry, or create one, instead of importing another module's classes. Cross-module Blade partials (`<module>::partials.*-section`, `member-summary` …) are the other sanctioned coupling.

Navigation has two levels. The blue bar (`resources/views/components/layouts/app.blade.php`) is global only: Dienstausweis, bell, the 3×3 menu (`x-app-launcher`, on phones also Profil and Admin), Profil and "Admin" (always `/admin`, for everyone who can access the panel); never put module links there. Each module registers its **Modulleiste** in `boot()` with `ModuleRegistry::navigation($key, fn (User $u) => ['tabs' => [...], 'manage' => url])`, built with `App\Support\ModuleNav::tab($label, $route, $alsoActiveOn, $badge)` and returning null entries for what the user may not see; the main action of a page is never in the bar but once next to the page title (`<x-page-action :href>`), and pages don't repeat tabs as buttons; `x-module-bar` renders it under the blue bar for the module of the current route name (`<key>.*`, only with module access), and for every `/personalakte/*` page the Personalakte bar (Profil + `PersonnelFileRegistry` + Nachweise + Stunden). `PersonnelFileRegistry::section($module, $title, $livewireComponent)` puts a module's part right on the Profil instead of a tab (Einsatzbericht: Meine Einsätze, Schlüssel: Meine Schlüssel). `ModuleRegistry::register(..., startRoute: fn (User) => route name)` sets where the start page tile and the 3×3 menu open the module per user (`startUrl`; Personalverwaltung, Unterweisungen, Schlüssel: the module for role holders, the Personalakte/Profil for everyone else). Leaflet maps get `isolation: isolate` (app.css) so they stay under the header menus. Pages don't render their own tab bars; back links use the shared class `inline-flex … text-fw-navy`.

In `boot()`, each provider registers with the singleton `App\Services\ModuleRegistry` (key, name, roles, start route, optional restricted audience). It can also add start page cards (`DashboardRegistry`; `everyone: true` shows a card to every active Kamerad while the module is on, also without module access – Kalender next Termin, Übungsdienste next Dienst without topic via `ServicePlan::nextFor`, Lehrgänge own state), QR/barcode resolvers for `/i/{code}` (`ScanRegistry`), personnel file links (`PersonnelFileRegistry`), its gates and policies, Livewire aliases and scheduled commands. Whether a module is switched on is stored in the `modules` table (`is_active`, `auto_assign`, cached 60 s, cleared by `Module::booted`). Access and roles per user are in `module_user` (`User::canUseModule`, `User::hasModuleRole`). Admins may use every active module. Module routes use the middleware `module:<key>` (`EnsureModuleAccess`): an inactive module gives a 404 and a user without access gets a 403. Role checks are helpers on `User` (e.g. `canDecide()` = admin or role `entscheider` in `fahrzeugbuchung`).

The sections on bookings below describe `modules/Fahrzeugbuchung` (services in `src/Services`, tests in `tests/Feature/Booking`).

### Double-booking protection lives in the database
The `bookings` table has a GiST exclusion constraint `bookings_no_overlap` on `(vehicle_id, tstzrange(starts_at, ends_at, '[)'))`, `WHERE cancelled_at IS NULL AND status = 'confirmed'`. The intervals are half-open, so a booking ending at 14:00 and one starting at 14:00 don't collide. It needs the `btree_gist` extension. Application code catches SQLSTATE `23P01` / the constraint name and turns it into a `ValidationException`. Any new code path that writes bookings must do the same. Never weaken the constraint in favour of PHP-only checks.

### Booking status model
- `Booking.status`: `confirmed` | `pending` (a conflict request waiting for a decider) | `rejected`. Cancellation is the separate `cancelled_at`, not a status.
- `Booking::active()` = confirmed and not cancelled. These are the only bookings that block a vehicle. `Booking::visible()` adds pending requests; the calendar and monitor use it.
- `BookingDecision` (`pending` | `approved` | `rejected` | `withdrawn`) links a pending request (`booking_id`) to the confirmed bookings it overlaps (`conflicting_booking_ids`, JSON). It can also link to a booking the request would replace (`replaces_booking_id`). It keeps a JSON `history` log via `addHistory()`.

### Services own all state transitions
`BookingService` (create/update/cancel/availability) and `DecisionService` (request/decide/change/reopen/withdraw) are the only places that should mutate bookings and decisions. Livewire components and Filament resources call into them (e.g. Filament `EditBooking` calls `cancel()` and `releaseSlotsFreedBy()`). The cross-cutting rules that are easy to break:
- Members can't edit or cancel a booking once it has started. A running booking can only be ended early (`BookingPolicy::endEarly`, `BookingService::endEarly` sets `ends_at` to now), by its owner or by deciders/admins for anyone.
- After any update or cancel of a booking, `DecisionService::releaseSlotsFreedBy($booking)` must run. It automatically re-confirms the booking that lost an earlier decision once the winner no longer needs the slot.
- Cancelling a pending request means withdrawing its decision, not releasing slots.
- Decision mutations run in `DB::transaction` with `lockForUpdate`, so the first of two concurrent decisions wins.
- Deciders are active users with the module role `entscheider` in `fahrzeugbuchung` (the `users.is_decider` column is legacy and unused). If no active decider exists, the admins are used (`DecisionService::deciders()`). The `decide-bookings` gate is defined in `FahrzeugbuchungServiceProvider`.

### Notifications are synchronous and non-fatal
All mail is sent immediately; no queue worker is needed in production. Sends go through a wrapper (`DecisionService::notify`) that reports failures without throwing, so a mail error never rolls back the action. Notifications run after the transaction commits. Shared booking-formatting helpers are in `modules/Fahrzeugbuchung/src/Notifications/BookingSummary.php`.

Every notification to a Kamerad also lands under the bell in the header (Laravel `notifications` table, `App\Livewire\Notifications\Bell`, `/benachrichtigungen`). New notifications `use App\Notifications\Concerns\InApp;` instead of defining `via()`. The entry is taken from the mail (subject, first line, action URL), so the action URL must point to where the Kamerad has something to do. Login links and e-mail confirmations stay mail only. Every bell entry is also sent as web push (`App\Services\PushService`, listener on `NotificationSent` for the `database` channel in `AppServiceProvider`) to the devices in `push_subscriptions`; VAPID keys are generated on first use (setting `push.vapid_keys`, encrypted). `public/sw.js` (scope `/`) shows push and the `/offline` page; `/manifest.webmanifest` makes the app installable. Objektpläne keeps its own, more specific service worker.

### Scheduler and editable mail texts
- The production image runs `schedule:work` as an extra s6 service (`docker/s6-rc.d/laravel-scheduler`, after the migrations), so there is no separate scheduler container. Core schedules are in `routes/console.php`. Modules add theirs in their service provider via `callAfterResolving(Schedule::class, …)`. Every scheduled command must use `->appendOutputTo($output)` (container stderr, or `storage/logs/schedule.log`); otherwise Laravel sends its output and errors to `/dev/null`.
- `bookings:send-end-reminders` runs every minute. It claims each booking with an atomic `UPDATE … WHERE end_reminder_sent_at IS NULL` before mailing, so a second scheduler can't send duplicates. Changing `ends_at` resets the flag (`Booking::booted`).
- Admin-editable mail texts live in `mail_templates` (`MailTemplate`, Filament "E-Mail-Texte"). Defaults and placeholders are defined in code (`MailTemplate::defaults()` / `placeholders()`); rows are created on first use. To make another mail editable, add a key there and build the mail with `MailTemplate::for($key)->toMailMessage($values, $url)`.
- The reminder's "Fahrzeug ist schon zurück" button is a signed URL (`bookings.return`, no login). GET only shows a confirm button and the POST ends the booking, for the same mail-scanner reason as the magic links.

### Booking comments
Per-booking chat (`BookingComment`, Livewire `Booking/BookingComments`, embedded in the booking detail). Deletes are soft, and `BookingComment::edit()` stores the previous text in `booking_comment_revisions`. Only authors may edit or delete. `BookingCommentPolicy::viewHistory` (= `canDecide()`) controls who also sees trashed messages and revisions; members see only the "bearbeitet" marker.

### Feedback to admins
Member-to-admin threads (`FeedbackThread` / `FeedbackMessage`, Livewire `Feedback/*`, Filament "Feedback"), owned by `FeedbackService`. `unread_for_user` / `unread_for_admin` drive the red dot on "Profil" and the admin counter. A member reply reopens a closed thread. Mail failures are reported but not thrown, like in `DecisionService::notify`.

### Time zones
The app timezone is UTC and timestamps are stored as `timestamptz`. Everything is displayed in `Europe/Berlin`: explicit `setTimezone('Europe/Berlin')` in notifications, `->timezone('Europe/Berlin')` on Filament fields and columns, and the FullCalendar setup in `resources/js/calendar.js`. Keep this explicit when adding new time output.

### Auth and access
- Passwordless magic links (`MagicLinkService`, `MagicLinkController`): GET shows a confirm button and only the POST consumes the token, so mail scanners can't burn it. Tokens are SHA256-hashed before storage; only the raw token is in the mail. Rate-limited to 5 requests/hour per email and 20/hour per IP (`config/magic-link.php`), token routes `throttle:20,1` and constrained to `MagicLinkService::TOKEN_PATTERN` (404 otherwise). Emails are looked up trimmed and case-insensitive (`MagicLinkService::normalize`). Tokens are single-use, and a login deletes the user's other open tokens; unknown emails get the same response as known ones, and lookup, token and mail run in `defer()` after the response so timing doesn't tell them apart (Feature tests run deferred callbacks immediately, `tests/Pest.php`). Einladungen: QR on screen 30 minutes, by mail 48 hours (`Invitation::SCREEN_MINUTES`/`MAIL_HOURS`).
- `User.status` (`active` | `inactive` | `left`, `App\Enums\MemberStatus`) is the member status; `is_active` is the login flag derived from it in `User::booted` (writes to `is_active` alone are mapped back). Member data (department, rank, gender, notes) lives on `users`; modules don't keep their own member tables. Users referenced by bookings, comments or Kleiderkammer issuances can't be deleted plainly (`UserResource::deleteIfUnreferenced`); set them to `left`, or use "Löschen mit Übertragung" (`App\Services\MemberRemoval`). It reads every non-cascading foreign key to `users` from `pg_constraint` and moves it to another Kamerad (dropping rows that would break a unique key), so new modules are covered automatically. Exceptions: logs stay as they are (`KEEP`), and Verbandbuch person links are only emptied (`UNLINK`). Add new log or health-data columns to those lists.
- Members without login: `users.email` is nullable (e.g. Jugendfeuerwehr children, Musikzug). They are ordinary active users for every module (`User::active()` lists include them) but `User::hasLogin()` is false: `Invitation::create` refuses, `MagicLinkService::consumeToken` refuses, `canAccessPanel` is false, the admin hides Einladung/Login-Link; mail is skipped by Laravel's mail channel (null route), bell entries stay, Kalender guardian copies still go out. Never assume `$user->email` is a string.
- Middleware `active` (`EnsureUserIsActive`) wraps all authenticated routes. Filament `/admin` requires `is_admin` and `is_active` (`User::canAccessPanel`).
- `/fahrzeugbuchung/monitor/{key?}` is the read-only station board (`Livewire/Monitor/StationBoard`). It is accessible to admins, or with `DISPLAY_TOKEN` (`config/monitor.php`) compared via `hash_equals`. Everyone else gets a 404, not a 403. It shows names shortened ("Hanna H.").
- `ADMIN_EMAILS` are upserted as active admins on every container start (`docker/entrypoint.d/60-ensure-admins.sh` → `app:ensure-admins`).

### Other notable choices
- Admin "Analyse" (`App\Filament\Pages\Analytics`, `/admin/analyse`, admins only): reported exceptions go to `app_errors` via `ErrorRecorder` (registered in `bootstrap/app.php`, grouped by class and place, admins notified once a day per place); `RecordRequestMetrics` (global middleware) sums requests per hour and area (module key/`admin`/`kern`, Livewire updates by referer) in `request_metrics` – skipped in tests unless `config('app.record_request_metrics')`; `app:heartbeat` (every minute) writes `heartbeats` (uptime) and the version's first-seen date; scheduled-task events fill `schedule_runs`; `SystemStatus` holds backup reports (`/webhooks/backup/{token}`, `routes/webhooks.php` without session/CSRF), the TLS certificate, resources and `problems()`, mailed daily by `app:health-check`. `App\Services\Analytics` aggregates logs per module, never per person. Retention (`App\Support\Retention`, setting `analytics.retention`: technical/audit/mail days) drives the prunable models (`AppError`, `RequestMetric`, `Heartbeat`, `ActivityLog`, `MailLog`). Failed and throttled logins are activity events `login_failed`/`login_throttled` (a malformed token is refused without any query).
- Kalender Termin-Monitor: `/kalender/monitor/{key?}` (`kalender.monitor`, `Livewire\MonitorBoard`, `Roster::upcoming`), same access as the Wachen-Monitor (admins or `DISPLAY_TOKEN`, else 404).
- Activity log: every Eloquent create/update/delete of `App\` and `Modules\` models is written to `activity_logs` by `App\Services\ActivityRecorder` (wildcard listener in `AppServiceProvider`), with the user, the admin behind "Als Kamerad ansehen", and the changed fields. Secrets and file contents are masked by field name (`SECRET` pattern), bookkeeping fields are skipped (`BOOKKEEPING`), and log/token/history models are in `SKIP`. Keep these lists current when adding models with secrets or blobs. Sent mails are in `mail_logs` (`LogSentMail`) and also get an activity entry. Both prune after 180 days. Admin page: `LogResource` (`/admin/logs`).
- All URLs are German, like the UI: app routes (`/profil`, `/anmelden`, `/fahrzeugbuchung/kalender`) and the Filament panel. Every Filament resource and page sets `$slug` and resource pages use `/neu` and `/{record}/bearbeiten` instead of `create`/`edit`. The old English paths redirect (301) via the list at the end of `routes/web.php`; add new entries there when renaming. The signed return link of old reminder mails is kept as `fahrzeugbuchung.bookings.return.legacy`.
- There are no REST/API routes. All user-facing features are Livewire components; the admin panel is Filament. Plain controllers exist only where Livewire doesn't fit: magic link and e-mail change confirmation (GET shows the page, POST consumes), `BookingEventController` (FullCalendar JSON), `BookingReturnController` (signed return URL), `ScanController` (`/i/{code}`), defect photos, the Kalender `.ics` feeds and public calendar, and the DIVERA webhook (`/webhooks/divera/{key}`, Einsatzbericht).
- Avatars are stored as base64 WebP in the `user_avatars` table, not on disk (`AvatarService`). Served from `/avatars/{user}?v={timestamp}` with immutable cache headers; the `?v=` param changes when the avatar is updated, busting the browser cache.
- Verbandbuch (`modules/Verbandbuch`) holds health data: its text fields use the `encrypted` cast, its models are in `ActivityRecorder::SKIP` (it keeps its own `vb_access_logs`), and its mails carry no health data. Postgres triggers make signed entries, signatures and Nachträge immutable and block deletes before `retain_until` (10 years, `Entry::RETENTION_YEARS`; the trigger lets it grow, never shrink; only `model:prune` removes them). Functions created in migrations must use `CREATE OR REPLACE`, because `migrate:fresh` drops tables but not functions.
- Unterweisungen (`modules/Unterweisungen`, tables `uw_*`): kinds with interval and audience (`for_all`, `group_ids`, `function_ids` JSON), sessions with attendances signed on screen (`SignatureImage`); the state is computed (`InstructionService::stateOf`/`matrix`). `counts_as = atemschutz` feeds `Atemschutz\…\ReadinessService::fromUnterweisungen`. `DriverRegistry` now takes several providers (Führerscheine: classes and drivers, Unterweisungen: vehicle Einweisung warnings), and the core `App\Services\BadgeRegistry` collects Qualifikations-Kürzel per Kamerad from the modules (shown in the Personalverwaltung list).
- Führerscheine (`modules/Fuehrerscheine`, tables `fs_*`): photos (`fs_photos`) live only until the decision (`LicenseService::decide` deletes them); `fs_checks` keeps a snapshot of every check. Who may drive what goes through the core `App\Services\DriverRegistry` (`warning`, `drivers`), which Fahrtenbuch (TripForm) and Fahrzeuge (vehicle detail) ask without knowing the module; requirements come from `fv_profiles.license_class` or the weight. Expiry dates are synced as invitee-only Kalender events (`managed_by = fuehrerscheine`).
- Expositionen (`modules/Expositionen`, tables `ex_*`): Gefahrstoff exposures (GefStoffV § 14). `activity`/`substances`/`notes` use encrypted casts, the models are in `ActivityRecorder::SKIP` (`ex_events` is their own who-did-what log), `retain_until` = 40 years and a trigger blocks deleting non-draft rows before it (`model:prune` removes them later). `MemberRemoval` only unlinks `ex_exposures.user_id`/`recorded_by` (the name stays in `person_name`). `ExposureService::proposeForCrew` creates drafts from an Einsatzbericht crew (Atemschutz pre-filled); `openPrompts` asks after Brand-Einsätze. There is no ZED API: the Meldeliste exports CSV and marks rows reported.
- Wartung (`modules/Wartung`) has no device list of its own: it builds on Ausrüstung's `ar_equipment`/`ar_categories` and writes results back through `Ausruestung\…\EquipmentService` (`recordInspection`, `reportDamage`). `WartungService::ready()` checks that Ausrüstung is active. Signed `wm_protocols` and `wm_attachments` are protected by triggers like the Verbandbuch.
- Atemschutz (`modules/Atemschutz`) reads Lehrgänge (`lq_records`/`lq_courses`, matched by course name) only while that module is on, reads back Einsätze marked `eb_report_crew.breathing_apparatus` (non-draft reports, `ReadinessService::reportMissions`) for the yearly Einsatz/Übung, and writes to the Einsatzbericht (`eb_report_crew.breathing_apparatus`) and its views (`atemschutz::partials.report-section` is included from Einsatzbericht's report and print pages). Readiness is computed (`ReadinessService`), not stored – including the CSA readiness (`state['csa']`: `is_csa` + CSA-Übung within 12 months from `csa_uebung`/`csa` trainings or `as_teams.csa`) and the Tragezeit by kind (`wearTime`, `WEAR_KINDS`); `atemschutz::partials.member-status` shows it in the Personalverwaltung.
- Fahrzeuge (`modules/Fahrzeuge`) has no vehicle table of its own: it adds `fv_profiles` etc. to Fahrzeugbuchung's `vehicles` (shared with Einsatzbericht). Its downtimes block bookings through the core `App\Services\VehicleBlockRegistry`, which `BookingService` (`checkAvailability`, `create`, `update`, `assertNotBlocked`), `DecisionService::request` and `BookingEventController` consult – so Fahrzeugbuchung never references Fahrzeuge. New code that books vehicles must call `assertNotBlocked` too. A Prüfung (`FleetService::recordWork` with `result`/`checklist` from `fv_deadlines.steps`) sets the status (`status_source = inspection`, so only a status a Prüfung set is lifted by a passed one; failed keeps the deadline open) and reports each step with a Mangel to Mängelmanagement (`mm_defects.vehicle_id`). Deadlines are mirrored as Kalender events for the Fahrzeugwarte (`fv_deadlines.event_id`, `managed_by = fahrzeuge`, `syncCalendar`); `fv_documents` hold the Fahrzeugakte (base64, `internal` = Fahrzeugwarte only); `submitToFinance` hands costs to Finanzen as an Ausgabe; vehicle QR labels use the scan code `FZ-<id>`.
- Fahrtenbuch (`modules/Fahrtenbuch`) logs trips of the shared `vehicles` and writes the Kilometerstand back into `fv_profiles` (Fahrzeuge); one open trip per vehicle is a partial unique index (`ft_trips_one_open`). Trips are never deleted: corrections go through `LogbookService::correct` (revision with reason), wrong trips are voided.
- Wasserkarte (`modules/Wasserkarte`): QR labels use the scan code `WK-<id>` (`Source::scanCode()`, resolved via `ScanRegistry`). `WaterService::nearest()` (haversine in PHP) feeds `wasserkarte::partials.report-section`, which Einsatzbericht's report and situation pages include. Maps are Leaflet/OSM via `resources/js/water-map.js` (`waterMap`, `waterPicker`); Livewire pushes changed markers with the `water-markers` browser event.
- Objektpläne (`modules/Objektplaene`, tables `op_*`): files are base64 in `op_versions.data` (never updated; a new upload is a new version, `Document::current` is the highest). `ObjectPlanService::near()` (haversine, object `radius_m` + `TOLERANCE_METERS`) feeds `objektplaene::partials.report-section` (Einsatzbericht report and situation pages), the TOP start page card and the library. Offline: `resources/js/object-plans.js` registers the module's service worker (`modules/Objektplaene/resources/js/sw.js`, served by the route `objektplaene.worker` with `Service-Worker-Allowed: /objektplaene`) and sends it `offlineUrls()`; plan files are cache-first (immutable), module pages network-first.
- Personalverwaltung (`modules/Personalverwaltung`, tables `pm_*`): the Diensthistorie in `pm_history` also holds manual Ereignisse (`kind = event`, one date, never "current" – use `isCurrent()`, not `until === null`) and Dienstzeiten in other Wehren (`service`), with Nachweise in `pm_history_files` (base64). The anrechenbare Dienstzeit (`Support\ServiceTime`: Aktiv periods + `service`, minus Jugendfeuerwehr per `PersonnelService::serviceRules()`) drives the Dienstjahre and `dueHonors()`. The career is synced from the member data by `PersonnelService::syncHistory()` (on `User::saved`, after the request so pivot syncs are in, and hourly via `personalverwaltung:sync-history`); open rows (`until` null) mirror the current state, manual rows need an `until`. Personalverwalter can be scoped to Abteilungen (`pm_scopes`, `PersonnelService::visibleMembers()`); the Dienstbeteiligung is computed from Kalender attendance (`kal_responses.attended`), not stored. Personal data (address, birth date, phone on `users`) is switched on per field by the Personalverwalter (`PersonnelService::settings()`, setting `personalverwaltung.fields`), independent of the global `App\Support\MemberFields` (which stays off for the rest of the app); self-service changes notify the responsible Personalverwalter (fields only, no values), and `ActivityRecorder::PERSONAL` hides the values in the log. Its role pages (Neue Mitglieder, Änderungswünsche, Einstellungen …) are tabs of its Modulleiste, and `PersonnelFileRegistry::register()` takes an optional visibility closure.
- Lehrgänge (`modules/Lehrgaenge`, tables `lq_*`): a completed `lq_records` row is a qualification, whether it came through the registration flow or was entered afterwards by the Ausbildungsleiter (`RegistrationService::recordCompleted`, `entered_manually`; for many Kameraden at once `recordCompletedMany`; the date is optional, so `completed_on` may be null on completed rows – readers must cope). A `requested` row with `waitlisted_at` is registered in fox112 (Warteliste, `Record::isWaitlisted()`); `cancel_seen_at` marks an Absage as signed off, and the start page counts only `requested` without `waitlisted_at` and `RegistrationService::unseenCancellations()`. Admins and Ausbildungsleiter correct any completed record (`updateCompleted`) and delete it (`deleteCompleted`); with a reason the deletion is documented in `lq_deletions`, without one the row is simply gone (hard delete, so modules reading `lq_records` directly need no `deleted_at` filter). Other modules read completed records (Atemschutz readiness, Jahresbericht, Personalverwaltung via `lehrgaenge::partials.member-summary`). The Lehrgangsplan is computed from `lq_record_sessions` (`Support\CoursePlan`). `lq_courses.repeat_months` gives a refresher interval (`Record::validUntil()`/`refreshState()`, `lehrgaenge:remind-refresh`); a later date of the same course in `recordCompleted` is the Auffrischung. `Services\ResultImport` imports results of external Träger from CSV (preview, then `recordCompleted`). The fox112 import (`CatalogImporter`) never offers or deletes by itself: `lq_courses.is_standard` means offered (set only by the Ausbildungsleiter), new or removed courses get `suggested_at`, `ignored_at` stops suggestions, offered courses that left fox112 get `gone_since`; a course with records is only hidden (`removed_at`, scope `onList`), so `offered()` = `is_standard` and not removed.
- Erziehungsberechtigte (`guardians`, `App\Models\Guardian`, notifiable by mail, no login): `Kalender\…\EventService::notify()` sends them `GuardianCopyNotification` (a copy of the child's Kalender mail) with a temporary signed link to `kalender.guardian` (GET shows, POST answers via `respondAsGuardian`). Their email/phone are masked in the activity log. Ansprechpartner are `contacts` (Filament `ContactResource`, page `/ansprechpartner`).
- Stundennachweis: modules register hour rows with `App\Services\HoursRegistry::register($module, $source, fn (array $userIds, Carbon $from, Carbon $to) => rows)` (Kalender attendance, Einsatzbericht crew of DONE reports, Lehrgangstage with times, confirmed Schichten); `/personalakte/stunden`, Personalverwaltung `/personalverwaltung/stunden` and its Jahresbericht section read them, `App\Support\HoursCsv` exports. Nothing is stored. `kal_events.partners` holds the partners of a gemeinsame Übung.
- Einladung: `App\Services\Invitation` creates a LoginToken (an ordinary magic link, single use; on screen `SCREEN_MINUTES`, by mail `MAIL_HOURS`) for QR code or mail (`InvitationNotification`, mail only); `MagicLinkService` flags the first login and the controller sends it to `/willkommen`. Personalverwaltung has two roles: `personalverwalter` edits (`canManage`/`mayView`), `personaleinsicht` reads (`canView`/`mayRead`, gate `personalverwaltung-view` on the read routes); `createMember`/`importPreview`/`importApply` take in new Kameraden.
- Digitale Nachweise: modules register cards with `App\Services\CredentialRegistry::register($module, $title, cardFn, verifyFn)` (Atemschutz: Atemschutzpass; Führerscheine). The Dienstausweis (Personalverwaltung, setting `digital_id`, plus `id_issuer`, `id_birth_date`, `id_birth_on_check`, `id_require_number` in `PersonnelService::settings()`; Geburtsort in `pm_profiles.birth_place`) registers only its verify part; its card (`personalverwaltung::credentials.id-card`) mirrors the official ID-1 layout in the app's colours and without coats of arms (it is the digital copy, never an imitation of the official card), sized in `cqw` inside an `@container`; it has its own page `/dienstausweis` (`personalverwaltung.digital-id`, auth+active, no module access needed) behind the card icon in the header, shown when `PersonnelService::digitalIdFor()` returns one. `/personalakte/nachweise` shows them with a QR code to the temporary signed route `credentials.check` (10 minutes, no login), which renders the verify parts only for active members. Personalverwaltung's Sammelverarbeitung (`PersonnelService::promote` – gender-aware via `FireRanks`, dates the history entry –, `awardMany`, `setFunction`) and Auswertungen (`report()`) work within `visibleMembers()`; Änderungswünsche are `pm_change_requests` (`PersonnelService::requestChange` / `answerChange`).
- Mitteilungen (`modules/Mitteilungen`): audience by `announcement_group` and `announcement_function` (sub-functions included); `AnnouncementService::recipients()` is the one place that resolves it (mail, push, read stats). Attachments are base64 in `announcement_files`; `announcement_reads` keeps read_at/acknowledged_at for the Lesebestätigung (`needs_ack`, `stats`, `remindUnacknowledged`).
- Shared lists: `places` (`App\Models\Place`, name + address → `navigationUrl()`) and `dress_codes` (`App\Models\DressCode`) belong to the core. Each module that uses them shows the shared editor `App\Livewire\Catalog\PlacesAndDress` in its own menu with its own gate (`ability`, e.g. Kalender `manage` on `Event`, Übungsdienstplaner `plan-uebungsdienste`), so all modules edit the same rows. Forms include `partials.place-dress-fields` (Livewire props `placeId`, `location`, `dressCodeIds`), views `<x-place-info>` / `<x-dress-codes>`; free Ort fields can use `partials.place-datalist` (`list="openwehr-places"`), and `Place::forLocation()` gives a matching free text its address.
- Übungsdienstplaner roles: `ServicePlan::canPlan` = admin or role `übungsdienstplaner` (create, change, delete, topic, responsible); `ud_scopes` limits a planner to Abteilungen (`scopeOf`, none = all), `ud_services.owner_group_id` is the Abteilung a Dienst belongs to (null = whole Wehr; target group defaults to it), `mayEdit`/`visibleTo` apply it. Everyone else with access only swaps: `ud_swaps` (`requestSwap` → the other responsible Kamerad `answerSwap`s, `withdrawSwap`; pending swaps are shown to all). Vehicles of a Dienst (`ud_service_vehicles`) are booked through the core `App\Services\VehicleBookingRegistry` (Fahrzeugbuchung registers `vehicles`/`book`/`cancel`; `book` runs in its own transaction and throws a ValidationException when the slot is taken), 30 minutes before/after (`VEHICLE_BUFFER_MINUTES`); reschedule rebooks, delete cancels. Use the registry, never Fahrzeugbuchung's classes, to book from other modules. Role labels in the admin use `mb_ucfirst` (umlaut role keys).
- Kalender Terminarten are rows of `kal_types` (`Kalender\…\Models\EventType`: key, label, hex color, order, active; read once per request): use `Event::types()` for choices, `EventType::labels()` for validation and lookups, `labelOf`/`colorOf`/`styleOf` for display – there is no `Event::TYPES` constant any more. Keys other modules write (`EventType::PROTECTED`: uebung, veranstaltung, wartung, sonstiges) can't be deleted. Admin page `kalender.types`. Start page cards show `<x-countdown :at :all-day>` (`App\Support\Countdown`, recalculated in the browser).
- Kalender Dienstplan: `Kalender\…\Support\Roster::rows()` (year or half-year, Abteilung, types; only `visibleTo`, no cancelled, invitee-only, `managed_by` fuehrerscheine/fahrzeuge or external events) feeds the print page `kalender.roster` (`/kalender/dienstplan`); `kal_events.organizer` is the "Ausführend" column (Übungsdienste copy `ud_services.organizer`).
- Übungsdienstplaner → Kalender: `Uebungsdienste\…\CalendarLink` keeps one event per Dienst (title "Übungsdienst", type `uebung`, `managed_by = uebungsdienste`, target group, place, Kleidung – never topic or responsible people); hourly `uebungsdienste:sync-calendar` adds missing ones but not ones deleted in the Kalender (`calendar_synced_at`). `kal_events.managed_by` marks events kept by another module (also Schichtplan).
- Schlüsselverwaltung (`modules/Schluessel`, tables `sk_*`): keys reference the shared `places`, `vehicles` and `op_objects`; one open handover per key is a partial unique index (`sk_handovers_one_open`); the signature of the Schlüsselquittung uses `App\Support\SignatureImage`. Other modules show keys via `schluessel::partials.keys-for` (Objektpläne object, Fahrzeuge vehicle) and `schluessel::partials.held-by` (Personalverwaltung).
- Mängelmanagement (`modules/Maengelmanagement`, tables `mm_*`): `DefectService` owns every change (report, setStatus, setUrgency, assign, comment, `ask` = Rückfrage with `mm_defects.question_open_at`, closed by the reporter's answer, `reopen` within `Defect::REOPEN_DAYS`, `remind` claims via `reminded_at`); `canEdit` = Verantwortlicher or Zuständiger, who edit on the detail page. Comment photos hang on their event (`mm_defect_photos.event_id`; `Defect::photos()` are only the report's). A defect can concern a device (with `responsible_id` → auto-assigned), a vehicle or an Ausrüstung item (`equipment_id`; creates an `ar_damages` row, `ar_damage_id`, repaired when the defect is resolved).
- Bestand (`/bestand`, `App\Livewire\Inventory\Search`): modules register a search and optional Ersatzbeschaffung rows with `App\Services\InventoryRegistry::register($module, $label, fn (string $term, User $user) => rows|null, fn (User $user, int $from, int $to) => rows|null, $order)`; return null for users who may not see the module's objects (Fahrzeuge, Ausrüstung, Kleiderkammer, Schlüssel, Mängelmanagement do). An exact code opens via `ScanRegistry::resolveKnown()` (resolvers without fallbacks). Ausrüstung items carry an RFID/NFC tag (`ar_equipment.rfid`, normalised by `Equipment::normalizeTag`, found with `findByScan` together with code and barcode); Web NFC (`NDEFReader`, serialNumber) is used in the Bestand, the Inventur and to learn tags. Inventuren are `ar_stocktakes` (`StocktakeService::finish`), Reinigung/Wartung costs sit on `ar_events.cost` (`logWork`, `lifecycleCosts`); vehicles have `fv_profiles.replacement_year`/`replacement_cost_cents`.
- Ausrüstung "Geräteinfo ohne Login": `Ausruestung\…\Support\PublicScan` (setting `ausruestung.public_scan`, Filament page `PublicScanPage`); the scan resolver sends guests to `ausruestung.public` only while it is on.
- Einsatzbericht states: `draft` (Entwurf, not started) → `active` (Aktuell, started via `ReportService::start` or from DIVERA) → `closed` → `released`; `Report::OPEN` / `Report::DONE` group them. "Running" (Lagemeldungen, external QR, Atemschutz, Fahrzeuge "Im Einsatz") means `active` without `ended_at` (`Report::isRunning()`), never `draft`. Address suggestions come from `App\Services\AddressSuggestions` (Google Places API (New), server-side with the stored key).
- Einsatzbericht extras: guided Zusatzangaben per Einsatzart are defined in `Support\ReportDetails` (stored in `eb_reports.details`, cleaned to the category in `ReportService::update`, requirable as `details`, counted by `ReportDetails::statistics`). `close`/`release` take an optional signature (`closed_signature`, `released_signature`); `release` stores `released_hash` = `ReportService::contentHash()` and `sealIntact()` compares it. Nebenberichte have `parent_id`/`side_label` and number `<parent>-n` (`createSide`); statistics count only reports without `parent_id` as Einsätze but crew-based figures over all. `einsatzbericht:remind` claims via `reminded_at`.
- Only released Einsatzberichte count in statistics, consumption and the Jahresbericht (`ReportService::countedStatuses()`, setting `einsatzbericht.released_only`, default on). The Personalakte still counts closed and released ones.
- Jahresbericht (`/einsatzbericht/jahresbericht`, Wehrführung): each module adds a section in its provider via `App\Services\AnnualReportRegistry::register($module, $title, fn (int $year) => html, $order)`; inactive modules and empty sections are dropped. New modules with yearly figures should register one.
- Finanzen (`modules/Finanzen`, tables `fin_*`): `FinanceService` owns every change. Settings (`FinanceService::settings()`, setting `finanzen.settings`): `budget` and `report` (Jahresabschluss) can be switched off – check `budgetEnabled()`/`reportEnabled()` before showing or changing budgets or closing a year –, and `public` decides whether everyone sees the overview (`canSeeOverview`); otherwise Kameraden see only their own entries and the full picture is for `canReview` (Kassenwart, Wehrführung, admins).
- Kleiderkammer member messages (`kk_equipment_messages`, `EquipmentMessageService`): `kind` = `defect` (Mangel) or `washing` (Wäsche anfordern, body = required reason, several items at once via `requestWashing`); `markWashed` closes it, writes a `kk_item_treatments` Wäsche for tracked items and tells the member.
- Shared helpers in `app/Support`: `SignatureImage` (checks the PNG from `partials.signature-pad` / `resources/js/signature-pad.js`) and `Money` (German euro amounts in cent).
- New instances start empty: vehicles, Abteilungen and Funktionen are created in the admin area. `2026_09_28_000000_seed_base_data` is an empty migration kept for the history; the seeders are for local dev.
- `trustProxies(at: '*')` is set because the app runs behind a reverse proxy (e.g. Coolify).
- No indexing: `public/robots.txt` disallows everything (AI crawlers named too) and the global middleware `App\Http\Middleware\NoIndex` sets `X-Robots-Tag` on every response; HTML layouts also carry `<meta name="robots" content="noindex, nofollow">`. The project page in `docs/` is the opposite: meant to be found.

## Security
CI (`deploy.yml`, job "Security Checks", on every push and pull request): `composer audit`, `npm audit --omit=dev --audit-level=high`, Larastan (`phpstan.neon`, level 5, module migrations listed under `databaseMigrationsPath`) and Gitleaks; the image is scanned with Trivy (critical, fixed) before it is pushed. `security.yml` repeats the audits and scans `latest` weekly; `security-review.yml` runs Anthropic's Claude Code security review on pull requests when the secret `ANTHROPIC_API_KEY` is set; Dependabot (`.github/dependabot.yml`) proposes updates weekly. Rules for new code:
- Serve stored uploads only through `App\Support\FileResponse::make($bytes, $filename)` (type by extension, inline only for PDF/images, sandbox CSP); validate uploads by extension (`FileResponse::allowedExtensions()`), never trust `getMimeType()` for serving.
- CSV exports use `App\Support\Csv::put()` instead of `fputcsv()` (formula injection).
- Outbound requests to user-entered URLs go through `App\Support\SafeUrl::get()` (public IPs only, pinned, redirects re-checked); tests resolve hosts via `SafeUrl::resolveUsing()` (set in `tests/Pest.php`).
- Login links shown on screen: `Invitation::createForScreen($member, $by)`; mails carrying login or action links belong in `LogSentMail::SENSITIVE`.
- `App\Http\Middleware\SecurityHeaders` sets the headers (CSP report-only; pages meant for iframes go into `EMBEDDABLE`). URLs are forced to `APP_URL` in `AppServiceProvider`; Livewire updates re-run `active` and `module:` via `addPersistentMiddleware`.
- Livewire props holding ids of records the user must not switch get `#[Locked]`; components that load a record by id authorize it.

## Deployment
The app version (`config/app.php` → `version`, e.g. `V.0.5.8`) is bumped by hand and shown small behind the admin title in the top bar (`brandLogo` → `resources/views/filament/brand.blade.php`). Each version gets a GitHub release with the tag in lowercase semver form (`v0.5.8`) and the title as written (`V.0.5.8`); versions may have two to four parts (`V.0.9`, `V.0.8.9.1` → tags `v0.9`, `v0.8.9.1`), which `release.yml` accepts.

A push to `main` runs the tests, builds the image and pushes it to `ghcr.io/roberteinsle/openwehr` (tags `latest` and `sha-<commit>`). If `COOLIFY_DEPLOY_ENABLED` is set, a Coolify webhook then redeploys a test instance (`latest`, sample data only). Production instances run a pinned release tag and are updated by hand after a DB backup, never by a push. Migrations run automatically on container start (`AUTORUN_ENABLED=true`), so every migration must also work on a fresh database and on existing installs (`tests/Unit/FreshInstallTest.php`). The installation guide for operators is in the README (UpCloud VM + Coolify).
